# `chunks.dat`（Survivalcraft）与 `bwebp`（本仓库）格式效率对比

> 甲：Kaalus《Chunks.dat File Format》<https://kaalus.wordpress.com/chunks-dat-file-format/>（1.4–2.2 四代规范；2.3+ 见《Boring Optimizations》）
> 乙：本仓库 `study-webp.md` 所描述的 bwebp v3，落地代码 `../bwebp.js`，格式文档 `../doc/xyzb/chunks_dat.md`
> 口径：格式成本按规范算（[推算]）；编码收益在同一份合成体素上复刻四种编码后用 Node zlib 实测（[实测]），参数见 §7。
> 注意：甲是**格式规范**，乙是**一篇代码评审**。对比以 `bwebp.js` 为准，`study-webp.md` 只作旁证。

---

## 0. 结论

1. **差距的主轴是"压不压缩"，不是"2 字节/格 vs 调色板"。** 1.28 的 66,576 B/区块是**裸数组**；任何一种压缩一上，同数据立刻掉到 2–8 KB。bwebp 相对 1.28 的 29×（自然地形）里，绝大部分来自 deflate/brotli，palette+bitpack 相对"u8 列 + 同一压缩器"只再省 0–38%（高熵时甚至输）。
2. **对 1.28–2.2：自然地形 29–50×，建造区 8–11×，极端高熵只有 1.4×。** 1000 个已改区块换算：64.2 MB vs 2.2 / 7.8 / 46 MB。
3. **对 2.3 的 RLE+deflate：1.0–1.2×（同为整列单流），按 2.3 的"每区块 + 1 KiB 预留"落地则 1.2–1.8×。** 两者编码强度是同一档，**bwebp 没有数量级优势**——它的护城河是"一张图就是存档"，不是压缩率。
4. **chunks.dat 赢在三个非体积维度：** 区块级随机访问（不必解压全部）、写放大只有 1 个区块、加载零解码。2.3 用"区域文件 + 每区块压缩 + 1 KiB 预留"保住这三项，bwebp 全丢。
5. **bwebp 真正浪费的两处都不在体素列：** ①`head` 完全不压缩（`bwebp.js:113`），一个满员 16K 格 BBat 组 = **43.7 KB base64 ≈ 19 个区块的压缩地形**；②palette 把光照也钉成 bitpack，导致"顺带存光照"比正确布局贵 **4.3×**（761 vs 175 B/区块）。

## 1. 两个格式各自在比什么

| 维度 | chunks.dat 1.4–2.2 | chunks.dat 2.3+ | bwebp v3 |
|---|---|---|---|
| 载体 | 独立二进制 `.dat` | 每区域一个文件（16×16 区块） | `.webp` 图片尾部（RIFF 后接 payload） |
| 记录单位 | 区块 16×16×128（2.2 起 256 高） | 同左，变长压缩块 | 区块 16×16×**128** |
| 稀疏性 | 只存 modified 区块 | 同左 | 只存 modified ∪ stored |
| 压缩 | **无** | RLE → deflate | palette+bitpack → deflate/brotli |
| 目录/索引 | 固定 786,444 B 目录（65536 槽 + guard） | 区域文件内 mini-FS | 无目录；`xz` 列 8 B/区块 |
| 元数据 | 16 B 头 + 1,024 B 表面点 | 同左 | `head` JSON（**不压缩**）+ `bio` 256 B |
| 实体/玩家 | 不在本文件 | 不在本文件 | `tiles`/`player`/`bbat` 全在 head |
| 完整性 | Magic1/Magic2，无校验和 | 同左 | 长度分帧，无校验和 |

稀疏性两者等价：都以"整区块"为单位，只在区块被改过时落盘。因此下面可以逐区块直接比。

## 2. 逐层成本

### 2.1 chunks.dat 的四代 [推算]

| 版本 | 区块体素数 | 方块字宽 | 字节/区块 | B/体素 | bit/体素 |
|---|---|---|---|---|---|
| 1.4–1.28 `Chunks.dat` | 32,768 | 16 bit（8 类型 + 4 光 + 4 数据） | 66,576 | 2.032 | **16.25** |
| 1.29–2.1 `Chunks32.dat` | 32,768 | 32 bit（10+4+18） | 132,112 | 4.032 | **32.25** |
| 2.2+ `Chunks32h.dat` | 65,536 | 32 bit | 263,184 | 4.016 | **32.13** |
| 2.3+ 区域文件 | 65,536 | RLE+deflate | 变长，见 §3 | — | — |

拆开看 1.28 的 66,576 B：方块 65,536 + 表面点 1,024 + 头 16。
其中**可重算的派生数据**：光照 4 bit = 16,384 B（24.6%），表面点 1,024 B（1.5%）——合计 **26.5% 是缓存，不是数据源**。砍掉光照后同格式应为 50,192 B/区块，但文件里没有这个变体。

### 2.2 bwebp v3 的记录布局 [实测]

`\b<len>:` 分帧，record 0 = JSON head，record 1..4 = `xz` / `b` / `m` / `bio` 四列；每列**单独一条** deflate 流，覆盖**全部**区块。

### 2.3 固定开销：786 KB 目录 vs 0

| 已存区块数 | 目录 | 区块体 | 目录占比 | 文件总计 |
|---:|---:|---:|---:|---:|
| 1 | 768 KiB | 0.06 MiB | **92.2%** | 0.81 MiB |
| 10 | 768 KiB | 0.63 MiB | **54.2%** | 1.38 MiB |
| 64 | 768 KiB | 4.06 MiB | 15.6% | 4.81 MiB |
| 1,000 | 768 KiB | 63.49 MiB | 1.2% | 64.24 MiB |
| 65,536 | 768 KiB | 4,161 MiB | 0.02% | 4,161.75 MiB |

bwebp 的对应固定开销：每列 4–9 B 分帧 + `xz` 8 B/区块 ≈ 40 B/区块，无目录；作为交换，`head` 是未压缩 JSON（§5）。**小世界（<100 区块）chunks.dat 的目录比数据本身还大**——这是它最不划算的区间。

## 3. 同一份体素，四种编码 [实测]

### 3.1 方法

合成体素（每场景 64 区块 = 8×8），三档熵：

- `terrain`：值噪声高度图 6–120、洞穴、矿石、y≤70 水体；palette 约 11 色。
- `build`：在 `terrain` 上叠 12×12×32 玩家建造体积，60 种方块 + 随机 meta；palette 约 61。
- `dense`：每格从 200 个 id 中随机取 + 16 档 meta，近最大熵；palette 200。

四种编码作用在**同一 payload**（方块 + 4 bit 数据，**均不含光照**，与两个真实格式一致）：

| 编码 | 说明 |
|---|---|
| `raw16` | 2 B/格交织（id + data），对照组 |
| `u8cols` | 两列 u8 拼接，对照组 |
| `pal` | bwebp：每区块 palette + ceil(log2) bitpack，按列整列压缩 |
| `rle` | 2.3：`[id][data<<4｜count≤15]`，超长另加 1 B |

### 3.2 结果（B/区块）

| 编码 | terrain（df/br） | build（df/br） | dense（df/br） |
|---|---:|---:|---:|
| `raw16` 整列单流 | 3,077 / 1,855 | 9,008 / 6,420 | 54,670 / 51,940 |
| `u8cols` 整列单流 | 3,150 / 1,877 | 8,863 / 5,779 | 51,465 / 47,988 |
| **`pal`（bwebp）** | **2,289 / 1,339** | **8,215 / 5,831** | **48,184 / 48,167** |
| **`rle`（2.3）整列** | **2,648 / 2,203** | **8,457 / 6,726** | **54,916 / 53,866** |
| `pal` 每区块单流（df） | 2,654 | 8,919 | 48,210 |
| `rle` 每区块单流（df） | 3,116 | 9,053 | 54,924 |
| chunks.dat 1.28（无压缩，含光照） | 66,576 | 66,576 | 66,576 |
| chunks.dat 2.1（无压缩） | 132,112 | 132,112 | 132,112 |

### 3.3 读数

1. **压缩器 > 变换。** brotli-11 相对 deflate-9（以 bwebp 自身为例）：自然地形 −41%、建造区 −29%、高熵 −0%。bwebp 只在**未压缩列 >50 MB** 时才升 brotli（`bwebp.js:117`），于是绝大多数存档跑在较弱的 deflate 上。降门槛（或统一 brotli）比换编码更划算。
2. **palette 与 RLE 是平手，各有主场。** 整列单流下 palette 分别好 1.16× / 1.03× / 1.14×（terrain/build/dense）；但 `build` 用 brotli 时 RLE 反而输 15%。换句话：**在"是否值得为体素换一种变换"这个量级上，两者差不到 20%**，而"有无压缩"差 20 倍以上。
3. **palette 的收益随熵升高而消失。** `terrain`：pal 2,289 vs u8 3,150（1.38×）；`dense`：pal 48,184 vs u8 47,988（**palette 反而略输**）。原因很直接——200 种方块时 8 bit 已经是信息量本身，bitpack 只删掉了熵编码器本来就会删的空码位；而 palette 每区块重排还会打断跨区块的匹配。**palette+bitpack 是"结构化数据"的特化优化，不是通用改进。**
4. **bitpack 会伤 deflate，尤其是低基数列。** 把光照也塞进 palette（3 bit 索引）：761 B/区块；普通 4 bit nibble 列：**175 B/区块**（4.3×）。bwebp 逐区块自适应调色板在"取值少、空间高度相关"的列（光照、群系）上是负优化——它把空间相关性换成了逐区块重编码。
5. **分帧粒度是隐形成本。** 从"整列单流"改"每区块单流"：RLE 在 terrain +18%、build +7%；palette +16% / +9% / +0%。bwebp 用整列单流换来最好的压缩率，代价是**没有区块级随机访问**（§4）。
6. **与文章自己的实测对齐。** 2.2→2.3 官方数字 2.78 GB → 26 MB（100×），反推约 10,562 区块、**2.40 KB/区块（含 1 KiB 预留）**，扣预留后 **1.40 KB/区块**。本实验自然地形 bwebp 为 2.29 KB/区块。**两个格式在同一量级**；文章的 100× 是"压缩 vs 不压缩"，不是"2.3 vs bwebp"。

## 4. 非体积维度

| 维度 | chunks.dat 1.28–2.2 | chunks.dat 2.3+ | bwebp v3 |
|---|---|---|---|
| 随机访问 | ✅ 目录 12 B → seek + memcpy，**零解码** | ✅ 区域 → 区块，需 inflate 该区块 | ❌ 每列一条流覆盖全世界，取一个区块要解压全部 |
| 加载 CPU | ≈0（memcpy） | inflate + RLE 解码 | inflate 全部 + 解包 + `recomputeHeights` + 光照 BFS |
| 写放大（改 1 格） | 1 个区块（66/132/263 KB）+ 12 B 目录 | 压缩块（≈2 KB）；1 KiB 余量内不重排，溢出才重写区域（256 区块） | **整文件重写**（所有已存区块） |
| 增量能力 | 区块级 | 区块级 + 预留吸收 | 无（`fill` 把读档区块全置 `modified`，下次全重编码，`bwebp.js:107`） |
| 崩溃安全 | 目录 + 魔数，原地覆写 | 区域重写（整块丢失风险） | 整文件重写；`dump` 非原子快照（`study-webp.md` P0-1） |
| 校验和 | ❌ | ❌ | ❌（`unpack` 越界静默，P1-8） |
| 版本门 | 无版本字段：靠 `Magic2`（`0xFFFFFFFF`/`0xFFFFFFFE`）+ 文件名 + 目录语义区分四代 | 同左 | `v` + `cols`，但 `cols` 要求逐字同序 → 加列即不兼容（`bwebp.js:57`） |
| 上限 | 65,536 区块、坐标必须为正、int32 偏移 ≤2 GB（2.1 改索引后 >4 GB） | 同上 | 1 B 方块 id（≤256）、**7 bit y（≤128，2.2 的 256 高做不到）**、`head.n` 不校验、单 Blob 受浏览器内存限制 |

一句话：**chunks.dat 是"文件系统"，bwebp 是"快照图片"。** 前者为随机读写设计，后者为整存整取设计；只比"每字节能装多少方块"，只覆盖了后者关心的那一半。

## 5. 存了什么：两者的分母不同

chunks.dat 只存地形（+光照 +表面点），玩家、实体、掉落物在别的文件里——66 KB/区块里**没有一分钱花在游戏状态上**。

bwebp 一个文件装完：`head` = `seed/time/player/inventory/tiles/bbat` + 封面。这个头**不压缩**（`bwebp.js:113`），且随每个存档复制一份：

| head 组成 | 未压缩体积 | 折合地形区块（按 2.29 KB） |
|---|---:|---:|
| 1 个满员 BBat 组（16384 格 × 2 B → base64） | **43.7 KB** | **≈19 个区块** |
| 1 个 27 格箱子 tile（JSON） | ≈0.6–0.9 KB | ≈0.3 个区块 |
| 玩家 36 格背包 + 状态 | ≈1–2 KB | ≈1 个区块 |

也就是说：**一个"只放了一组大建筑"的存档，head 的体积可以和它自己的地形一样大**，而且这些字节完全不参与压缩。chunks.dat 没有对应开销（它不存这些），这是它"看起来更省"的一部分原因，不是编码赢了。

反过来，bwebp 的封面也在文件里：1280×720 的 webp q0.85 通常 30–100 KB，**在小世界上比地形本身还大**。`doc/xyzb/chunks_dat.md` 的 "68 KB/64 区块" 与 `study-webp.md` 的 "1.06 KB/区块" 都只算列，不含封面与 head（后者 §3.2 已自我修正）。

## 6. 结论与可执行建议

### 6.1 对 bwebp（按收益/改动比排序）

1. **head 压成一条 record**（P1-6）。一个满员 BBat 组省 43.7 KB，胜过优化 19 个区块的体素列。注意 `headOf()` 靠"不解压就能读 head"支撑标题预览——要么留一条极简未压缩头（`v/enc/cols/n/cover`）再拆大字段，要么接受预览时要解压。
2. **降 brotli 门槛**（当前 50 MB 未压缩列，`bwebp.js:117`）。§3.3-1：自然地形 brotli 再省 39%，而 <50 MB 恰恰是最常见的存档。若担心 CDN 依赖（P0-4），先探测 `CompressionStream('brotli')`，可用即用。
3. **若将来存光照，用 nibble 列，不要走 palette。** 175 vs 761 B/区块（§3.3-4），且 nibble 列能直接喂给现有 `sky`/`blk`。
4. **`tiles`/`bbat` 移出 head 成列**（D6/D4）。顺带解决"标题页要解析全部箱子"（`doc/xyzb/chunks_dat.md` §2-5）。
5. **不要为压缩率改单文件模型**：换不来数量级（§3.3-2），却会丢掉"一张图即存档"。

### 6.2 从 chunks.dat 可以借的

1. **1 KiB 预留 + 区域重排**是 2.3 的核心 trick：用"隙"吸收小改动，把写放大从 O(world) 降到 O(chunk)，代价约 40% 空间。bwebp 若做分区块容器，这是现成模板（`study-webp.md` §1.2-2 结论相同）。
2. **魔数 + 冗余坐标**做廉价完整性检查：chunk 头里重复存 `ChunkX/ChunkZ`，读错位立刻暴露。bwebp 无等价物，`unpack` 越界静默（P1-8）——每区块加 4 B CRC32，比事后 debug 便宜。
3. **版本靠多信号而非一个整数**：chunks.dat 用 `Magic2` + 文件名区分 16/32 位与 128/256 高。bwebp 只有一个过严的 `v`（§4），加列就废——反而更脆。

### 6.3 对 `study-webp.md` 的口径补充

| 位置 | 现文 | 建议 |
|---|---|---|
| §0-1 / §3.2 | 引"64 区块 ≈ 68 KB"，容易被读成 bwebp 的通用压缩率 | 这是**某一世界**的实测；同数据本实验为 2.29 KB/区块（自然地形）到 48 KB/区块（高熵），跨度 21×。应写"1–12 bit/体素，取决于方块种类与建造密度" |
| §3.2 | "deflate-9" | 浏览器 `CompressionStream('deflate')` 不暴露 level（通常 zlib 6），68 KB 是基准值、非运行时值；§1.2-4 的 CDN brotli 也不固定 quality |
| §3.3 / §1.3 | 只讨论"存不存 ent/tiles/sched" | 还应加**编码层**结论：palette 对结构化数据有 1.2–1.4× 收益、对高熵无收益；把光照塞进 palette 反而贵 4.3×。这比"要不要存光照"更影响体积 |

## 7. 复现参数

- Node 26.7 `zlib`：`deflateSync({level:9})`、`brotliCompressSync({quality:11})`、`zstdCompressSync({level:19})`。
- 区块 16×16×128 = 32,768 格；每场景 64 区块（8×8），表中为 64 区块平均。
- `pack()` 逐行转写自 `bwebp.js:66-77`（YZX 序、`Int16Array(256)` 槽、LSB-first bitpack）；`rle()` 按《Boring Optimizations》的描述复刻（count 借光照 nibble，超 15 另加 1 B，超 255 再分片）。
- 合成生成器是**近似**，不是任何真实世界；结论按"同一 payload 下相对排序"使用，绝对值仅作量级参照。
- [推算] 数字来自规范算术（如 66,576 = 65,536 + 1,024 + 16）；[实测] 为本机 zlib 结果。
- 已知偏差：合成体素的熵低于真实 MC 类存档（真实区块压缩后通常 3–10 KB），故 `terrain` 列偏乐观；`dense` 列则刻意打到上限。真实值应落在 `terrain` 与 `build` 之间。
