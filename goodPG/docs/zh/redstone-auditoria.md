# 红石对照 Minecraft Java 的审计

将第 7 阶段的红石与 Java（1.21，26.x 的基础）进行对比，使其行为**一致**，技术上也是如此：0 tick 脉冲、BUD、准连接性、随位置和方向变化的行为、更新顺序。已经一致的部分不改动；不一致的部分则移植。

## 摘要

「普通」结果（一条红石粉线、一个时钟、一扇简单的活塞门）已经与 Java 一致。不一致的是**更新模型**，而技术电路正依赖于此：

| # | 主题 | Java | VoxelCraft（第 7 阶段） | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 通知顺序 | `NeighborUpdater` 深度优先：每个新通知都会在继续处理前一个之前被处理（如同传统的递归） | 广度优先队列（FIFO） | ✅ |
| 2 | 面的顺序 | `updateNeighborsAt`：西、东、下、上、北、南。形状：西、东、北、南、下、上 | +X、−X、+Y、−Y、+Z、−Z | ✅ |
| 3 | 每个方块通知谁 | 每个方块按 Java 规则通知：中继器通知前方方块及其邻居（不含自己）；拉杆通知自己的邻居以及所附着方块的邻居；火把通知其六个邻居的邻居…… | 所有变化都通知六个邻居；如果发出信号，还会通知相邻所有导体的邻居 | ✅ |
| 4 | 带选项的 `setBlock` | 位：1 通知邻居，2 发送到客户端，16 不更新形状……（中继器用 2 改变，并在 `onPlace` 中自行通知前方） | 所有变化都以相同方式通知 | ✅ |
| 5 | 形状更新 | 与通知分开（`updateShape`）：侦测器对它们作出反应；中继器的锁定也是如此 | 只有一种通知类型 | ✅ |
| 6 | `onPlace` / `onRemove` | 每个方块在放置和移除时执行自己的逻辑（在 `setBlock` 内部、通知邻居之前） | 之后统一的变更通知 | ✅ |
| 7 | 红石粉 | 逐线（`updatePowerStrength`）：每个都重新计算，并按 **`HashSet` 的顺序**通知自身及其六个邻居的邻居（因此行为随位置变化）。长线关闭时会逐渐降低 | 整个网络一次性求解（最终强度相同，顺序不同） | ✅ |
| 8 | 方块事件 | 活塞（以及音符盒、钟……）收到通知时不会立即行动：它们记下一个事件，在该 tick 的对应阶段处理，并在那时重新检查信号 | 活塞立即行动 | ✅ |
| 9 | tick 阶段 | 已计划的 tick → 流体 → 随机 tick → 方块事件 → 实体（压力板）→ 方块实体（移动中的方块、漏斗、阳光探测器） | 已计划的 tick → 踩踏 → 周期任务；活塞和漏斗之后 | ✅ |
| 10 | 移动中的方块 | 进度为 0 → 0.5 → 1 的实体（第三个 tick 落定）；活塞查看该进度来决定是否「吐出」（立即收回） | 固定 2 tick；如果在此之前断电则「吐出」 | ✅ |
| 11 | 已计划的 tick | 每个位置和方块类型一个；顺序（tick、优先级、到达顺序）；在 tick 期间计划的会被安排到下一个 | 相同 | ✅ |
| 12 | 信号强度（弱、强、导体、`getBestNeighborSignal`） | — | 相同 | ✅ |
| 13 | 中继器和比较器的延迟与优先级 | — | 相同 | ✅ |
| 14 | 火把烧毁（60 tick 内 8 次变化） | 每个世界一个全局列表 | 每个火把一个列表 | ✅ |
| 15 | 漏斗 | 方块实体：每个 tick、等待 8 tick；按方块实体的顺序 | 无事可做时休眠 | ✅ |
| 16 | 半途移动时保存的方块 | 保存进度并在加载时完成 | 按已落定状态保存 | ⚠️ |

## 已完成（并已验证）

- 引擎、红石粉、所有组件、铁轨、活塞、侦测器、漏斗、发射器和 TNT 都遵循 Java 代码（上表「VoxelCraft」列为改动前的状态）。
- 依赖 Java 内部顺序的部分（红石粉的 `HashSet<BlockPos>` 和活塞的 `HashMap<BlockPos>`）会与真正的 Java 比对：`tools/JavaHashOrder.java` 生成参考，`tests/redstoneJava.test.ts` 进行校验（300 个集合和 100 个映射，也包括大坐标）。
- 技术行为测试：粘性活塞以 1 和 2 tick 的脉冲吐出，并以 3 tick 拉回；准连接性可实现一个 BUD；烧毁的火把不会自行重新点亮（其 160 tick 的 tick 会被已有的 2 tick 覆盖而丢失），与 Java 相同。

## 决定与遗留事项

- **版本：26.3，已用其代码验证。** 最初从 Java 1.21.x 的代码移植，并与目录 JAR 的索引（`implementation.json`，仅签名）对照。之后阅读了 26.3 的代码：Mojang 发布的官方服务器 JAR（自 26.1 起未混淆；SHA-1 33680f5f…），仅在本地反编译作参考（其中没有任何内容进入仓库）。以下内容逐行一致：`CollectingNeighborUpdater`、`Level.setBlock`（发出通知的是旧方块）、通知与形状的顺序、`LevelTicks`、`ServerLevel.tick` 的各阶段、方块事件（无重复）、红石粉（`DefaultRedstoneWireEvaluator`）、火把、拉杆、按钮、压力板、中继器、比较器、侦测器、红石灯、铁轨、发射器、门、活板门、栅栏门、音符盒、钟、铜灯、TNT、漏斗和活塞（`checkIfExtend`、`triggerEvent`、`moveBlocks`、`PistonStructureResolver`、`PistonMovingBlockEntity`）。不一致并因阅读代码而修正的内容：
  - `affectNeighborsAfterRemoval` 只在变化带有选项 1 或由活塞移动时调用，并且仅当方块类型改变时调用；铁轨例外，它们在状态改变时也会收到。
  - `isHandlingTick`（使活塞立即收回的标志）从 tick 开始直到方块事件结束（也包括流体、随机 tick 和事件）都有效，而不只是在已计划的 tick 中。
  - 被活塞破坏的东西会变成空气（即使原本含水也不会变成水），并会单独收到其 `affectNeighborsAfterRemoval`，在通知之前。
  - 对红石粉的右键（十字或圆点）会通知那些因连接变化而导电的侧面方块（`updatesOnShapeChange`）。
  - 中继器若侧面被另一个二极管供电，放置时就已处于锁定状态（`getStateForPlacement`）。
  - 在 26.3 中，比较器读取时会接收其读取所经的面；现有的方块下没有变化（当出现按侧面读取不同的方块时，就需要用到它）。
- **发出通知的方块**在方块变化时是之前存在的那个（与 Java 的 `Level.setBlock` 相同）。一个有趣的效果在 Java 中也存在：把红石方块放在 T 形铁轨交叉旁不会改变它（通知来自原本的空气），而用拉杆或火把则会。
- **此处无法放入状态的属性**（门、活板门、栅栏门和钟的 `powered`，因为使用保存的 id）：它们位于按位置的数据中，其变化会像方块变化一样被通知（`stateTouched`：通知和形状，因此侦测器能看到它）。
- **放置：** Java 中由 `getStateForPlacement`/`setPlacedBy` 决定的内容（红石灯的点亮、1 tick 后点亮的中继器）会在放置后立即在 `placed` 中执行。
- ⚠️ **半途移动时保存：** 活塞半途移动时保存的区块会以已落定状态保存（Java 保存进度）。结果相同，只是该活塞在加载时不会重新检查信号。

## 计划（已执行）

1. **引擎**（`sim/server/redstone.ts`）：Java 的 `NeighborUpdater`（深度优先，带其上限）、带选项的 `setBlock`、`onPlace`/`onRemove`、Java 顺序的通知和形状、方块事件以及 tick 阶段。
2. **红石粉**：Java 的逐线算法，复现 Java `HashSet<BlockPos>` 的顺序（`BlockPos` 的 `hashCode` 以及 16 个桶的 `HashMap` 遍历）。
3. **组件**，逐一对照 Java 代码：火把、拉杆、按钮、压力板、绊线钩与绊线、中继器、比较器、侦测器、红石灯、音符盒、阳光探测器、标靶、避雷针、铜灯、门/活板门/栅栏门、铁轨、钟、陷阱箱、讲台、发射器、投掷器、漏斗、TNT、幽匿感测体。
4. **活塞**：方块事件、带进度的移动中方块实体、三种事件类型（伸出、收回、立即收回）以及推动解析器。
5. **测试**：使用已知装置（时钟、双稳态触发器、BUD、0 tick 脉冲、活塞门、随位置变化的行为），并保存移动内容的进度。
