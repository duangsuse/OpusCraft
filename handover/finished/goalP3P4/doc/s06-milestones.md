说明 / 发现：
- **comp\***：合成 pass 的独立计时（两帧之间画到同尺寸 RT）。帧内 comp 查询是当帧第一次写默认帧缓冲，会把等交换链/vsync 的时间也算进去（实测帧内 10–30 ms、与 DDA 成本无关），**不能作为合成本身的成本**，bench 表里另列「comp 帧内」只作参考。
- 列跳/砖/体素 = 主射线在三级上的平均步数；fetch 只计体素结构（`uVox/uBrick/uCol/uInfo`）与云纹理，不含图集/噪声采样。
- 平滑光照占比 = (dda − dda[DBG 3：本格光照、无 AO]) / dda。
- **水面是最大热点**：主射线 52 步、13% 像素耗尽预算，几乎全在体素级（32 步）—— 水体是「非空砖」，砖级跳不过去；远处平地视角的地平线水带同样是红色（见 `tools/out/bench/plain-iter.png`）。P2 的距离场/段跳要对水面单独看效果。
- 洞穴机位无光（全黑），只用于步数/着色统计；平滑光照占比在洞穴最高（22%）。
- 无头与有头（`--headed`）的 dda 数字同量级但有头更高、波动更大（桌面合成器共享 GPU）；对比请固定同一模式。

像素一致性：`--save NAME` 存每机位 ddaRT 原始像素到 `tools/out/ref/NAME/`，`--cmp NAME` 逐像素比较（同机重复运行 0 px 差异）。P1「画面与 P0 逐像素一致」即 `node tools/bench-v2.mjs --cmp p0` 四机位全 0 px。

### 6.3 P1 结果：`ChunkSource` + `BlockTable` + 段标记

实现（v2.js）：
- `ctx.source || voxelCraftSource(ctx)`、`ctx.blockTable || voxelCraftBlocks(ctx)`；v2 不再读 `ctx.chunks / c.blocks / RENDER…`。导出 `VR.source / VR.blockTable`。
- 相对 §2.1 的接口补充：`getChunk` 可返回 `light`（打包）**或** `sky`+`blk`（VoxelCraft 用后者，省一次打包拷贝），都缺省 = sky 15 / blk 0；新增 `forEachChunk(fn(cx,cz))`（`rebuildRing` 后整环重传要用）；VoxelCraft 适配器的事件源是 `buildChunk/disposeChunk`（`built/disposed`）。
- `BlockTable` 补充 `cullSelf[id]`（同种相邻不画内面，原来写死 `B.GLASS`）和 `waterId`；`uInfo.r` bit 6 = cullSelf。
- `H = source.height`（16 的倍数，≤256），shader 里 `#define H`；`${CH}/${B.*}` 全部去掉。
- 段标记**没有**单开 `uSect` 纹理，而是并进列纹理：`uCol` 改为 `RGBA16UI`（r = maxY+1，g = 区块坐标低 8 位 x | z<<8，b = 全空段掩码，a = 全不透明段掩码），换列时那一次 fetch 顺带拿到，零额外 fetch；同时 r 放得下 H=256。
- §3.3 的 `worldMaxY` 只在最高列下降时 O(N²) 重算。
- 槽位归属键改为 `"cx,cz"`（与宿主 `ck` 无关）；verify 跟着改，并新增「`VR.source.height` 与宿主一致」「列高/段掩码与区块数据逐块一致」两项。

结果（`--cmp p0`）：**四机位 0 px**；verify 全部通过。

**「步数在悬崖/洞穴机位下降」未达成，原因是数据而不是实现**：VoxelCraft 的地形里 16³ 段标记基本不会被置位（rd 6 全环 137 区块统计）：
- 列高以下的全空段 = 0 个（洞穴/悬挑从不会掏空整个 16³ 段；地表以上的空段已被列高跳过覆盖）。
- 全不透明段 = 0 个：地下段平均 92–95% 不透明、最高 4090/4096，但洞穴/矿洞的零星空格总会破坏「全实」。
- 因此 shader 段分支（`#if SECT`）从不触发，却让每帧慢约 2–3%（A/B 两轮：SECT=1 平均 +0.3–0.5 ms）→ **默认 `SECT: 0`**（`post.defines`），数据照常产出，留给 index.html（CHUNK_H=128、高空/地下大片整段）或 P2 用。
- 结论：洞穴/悬崖的步数只能靠 P2 的距离场降；§3.1 末尾「DF 上线后段级空标记可取消」在 VoxelCraft 上提前成立。SECT=1 路径目前**没有被画面验证过**（不触发），启用前需要构造整段全空/全实的测试世界。

#### 实现要点（按步）

- **第 2 步 云门控**（§9.2-1 = §4-2）：先 trace 再云；`tCl` = 可见表面距离（水面 `tw` / 命中 `tHit`；相机在水中且看不到水面 → 不追；上行射线耗尽 kind 4 → 不限）。`cloudHit/cloudVol` 多一个 `tLim`：**云层入口 `tE ≥ tLim` 直接返回**。因为 tc ≥ tE，而云只在 `tc·cosF < z` 时合成，这个门控**逐位精确**，不是近似（所以 0 px，连云边缘差异都没有）。风格 0/1 的云步本来就少，默认预设几乎不变；bliss canopy 25.3 → 15.4 ms。
- **第 3 步**：`isFluid()/fluidTop()` 收口（第 5 步后 `isFluid(uvec4)` 读 A 通道 FLUID 位，`${BT.waterId}u` 注入点 = 0）；`FLUID_TILE` 宏；`uFluidTop0 = −0.125`（meta 0 → 0.875，逐位等于旧常数）。`voxelCraftEnv(ctx)`（getter 包宿主状态；`underwater(flag, fog)` 里隐藏 `#water` 遮罩并按面板建议值写 `U.uFogNear/Far`；`hide('stars'|'clouds')`）；相机格判定走 `SRC.getBlocks`。verify 静态检查：v2 主体（适配器之前）不含 `ctx.skyMat/cloudMat/clouds/stars/getBlock/#water`。
- **第 4 步**：事件入口 `onChunkEvent(cx,cz,what)`：`'gone'`/null → 清槽位；同 `rev` 且已在槽位 → 跳过（`ring.dedup`）；`'light'` → `uploadLight` 只改镜像 G 通道 + 整块上传（不碰砖 / 列高 / 段 / 树叶后处理）；`'blocks'` → `uploadChunk`（`aux.maxY/sectEmpty/sectFull/brick/dist` 有就用）。CPU 镜像 `ring.mir[s]`（按需分配，布局同 uVox 一个区块），上传 = `stVox.image.data` 指向镜像槽位后 `copyTextureToTexture3D`（three r160 直接 `texSubImage3D(image.data)`，支持子盒）。宿主 A 适配器：`rev` = 全局 build 计数，`emit(c, what)` 供 verify 走 `'light'`。verify：三条路径各走一次、同 rev 去重、`aux` 生效。

- **第 6 步 P2 距离场**（相对 §3.4 / goal-renderapi 的改动已先写回 ts）：
  - **DF 只按本区块算，着色器把跳跃盒裁到当前区块 xz**：区块间零依赖 —— 邻块加载 / 卸载不需要重算，也没有「邻块已上传、本块 DF 未更新」的不安全窗口；Worker 变成无状态（主线程发占据数组 `{t:'occ'}`，Worker 只做截断切比雪夫变换 `dfTransform`，Blob Worker，无 Worker 时主线程同步算）。
  - **DF 占据 = occupied ∪ 流体表皮**（流体格且 6 邻有非流体；y 越界 / 跨区块邻格按非流体）。纯「不含流体」（TODO-2）时盒跳跃会整个越过水面（首次入水格 / 出水格都在盒里）；表皮保证入水 / 出水格必被逐格走到，内部水照跳。v2 的 halo / LEAVES_INNER 也算占据。
  - **走与跳同一条代码**：逐格层每轮算「以当前格为中心、半径 k 的盒（xz 裁到本区块）」的出口面，k = 0 就是普通一步；循环不再携带 `tM`（平面时间一律现算 `(平面 − ro)·inv`）。第一版（单独的跳跃分支 + 回砖级重入 + 4 个额外循环寄存器）**比不开 DF 还慢 10–25%**：spill 464，且只要跳跃代码存在（即便很少走到）就慢 3–5 ms —— 是寄存器压力，不是跳跃算术，也不是分叉。
  - **DF 开 / 关画面逐像素一致**的前提：任何路径到达同一平面的 t 逐位相同（现算平面时间）+ 出口轴平局优先级与步进分支的 `<` 比较一致（z > y > x）+ **精确入格**（每轴取最近格面、用同一式子算平面时间判断是否已跨过）。旧的进砖写法 `floor(ro + r·(t + 1e-4))` 在两个格面相距 < 1e-4 时会跳过一格、报砖入口的 t / 法线 —— plain 里那几个「草地上的黑点」就是它；改掉后对 `p1fx` plain 214 px、其余 ≤ 16 px（**这是对旧路径的修正**）。
  - **参考模式 `VR.setRef(1)` / bench `--ref` / 编译期 `REF_MODE`**：所有步数预算（主射线、阴影 20、反射/折射 64）放到 576 + 精确入格。精确入格默认 +5%（bliss +10%），所以**生产用 `clamp(floor(ro + r·t))`**（只在浮点舍入级平局上与逐格步进分歧：随机世界约每 6 个视角 1 px，两边同样安全）。DF 开/关 0 px 的验收一律在参考模式下做：verify、bench 5 机位、`tools/df-seeds.mjs` 60+ 个随机视角全部 0 px。只放大主射线预算不够——阴影 / 折射射线的固定预算会让 DF 开（走得更远）多出几 px 阴影差异。
  - 编辑安全：同一区块重传保留旧 dist；新占据格（旧值 ≥ 2）写 1 并在本区块内 `d = min(d, cheb+1)`（> 24 个 → 整块退回「未计算」）；变空的格保留 1。`onBlockChanged` → `EDITQ` → `flushEdits`（脏盒改镜像、整块重算占据、砖 / 列高 / 段从镜像重算、只传脏盒；树叶后处理开着时整块）。宿主 A 适配器不提供 `onBlockChanged`（宿主自己 build → `'blocks'`）。
  - 面板「距离场跳跃」（`df`，`#if DF`）；DBG 4 = R 盒跳跃次数 / G 砖级入口 v==0 退化 uBrick / B 逐格层遇到 DF 未回包；bench 列 `DF 跳/退0/退2`，`--probe x,y` 打印该像素 DF 关 / 开的 tHit / tw / 命中格（DBG 7/8/9）。
  - verify 新增：Worker 全部回包；**不变量 v−1 ≤ 真实距离**（按定义独立重算占据含流体表皮 + 26 邻膨胀求真实距离，12 区块 29 万格 0 违例，编辑前后各一次）；**1 格厚墙贴天空**放置 / 移除下一帧可见 / 消失（宿主 `setBlock` 路径与 `onBlockChanged` 脏盒路径各一次）；DF 开 / 关 steps 576 下 0 px。

#### 未达成项及原因

- **P3「核显 scale 0.8 四机位整帧 ≤ 12 ms」未达成**：最终 s+d+comp 19.7 / 16.7 / 10.3 / 33.0 ms（cave 达标）。原因：本着色器在 Intel 上编译为 **SIMD8 且有 ~230 个 spill**（`tools/shader-stats.mjs`），每多一个循环寄存器、每多一份内联 `trace` 都直接变慢；§4/§9.2 列的项目（门控、fetch 削减）在这个约束下收益有限，甚至为负（第 5 步）。阴影射线（第二份内联 trace）仍占 20–28%。
- **P2「四机位平均步数 ≥ 2× 下降」未达成**：÷1.41–1.68。剩下的步数主要是贴地掠射的体素步（离地 1 格的格子 d = 1，不能跳）和列跳；盒按区块裁剪让单次跳跃 ≤ 16 格。水面机位耗尽从 13% 降到 1%。
- **P2「主线程 updateChunks 耗时不升」只算部分达成**：整块上传的 CPU 部分（扫描 + 树叶后处理 + DF 占据 / min 更新 + Worker 拷贝）0.40 → 0.50 ms/块（`tools/upload-cost.mjs`，+0.1 ms 是每格的 DF 占据分类与 24 KB 拷贝，已并进原扫描、去掉第二遍）；同一块的 GL 上传是数 ms，且初次加载 rd 6 时 `updateChunks` 总耗时反而下降（GPU 帧更快、上传等待更短）。
- **`--cmp p1fx` 不是 0 px**：DF 开 / 关在预算放大时 0 px（verify + bench），但默认 `steps 128` 下 DF 让原先「耗尽 → 全雾」的像素走到真实命中（water 61191 px、uw 3436 px、plain 3463 px），加上旧进砖 ε 修正（plain 214 px）。另外：DF 让阴影（20 步）/ 水下折射（96 步）射线在预算内走得更远，于是画面开始依赖「环边缘那几列区块此刻是否已加载」——同一机位、不同的机位访问顺序，已加载区块集合不同（5 机位跑 185 槽、只跑 2 机位 166 槽），画面就差几千 px；固定机位序列时完全可复现（DF 不需要重算的公共区块逐字节相同）。基准一律用完整 5 机位序列。
- 第 7 步的 §4-5 与 §9.2-2 实现了但默认关（原因见上）。
